# App architecture: extending the scaffold

## What `solverforge new <name>` gives you

A web-shell project is a Rust/Axum backend plus a thin `static/` frontend that
already uses solverforge-ui.

| Path | Owner | Purpose |
| --- | --- | --- |
| `src/main.rs` | you | mounts `api::router(state)`, merges `solverforge_ui::routes()`, falls back to `ServeDir::new("static")` |
| `src/api/*` | you | `/jobs` and `/demo-data` routes plus SSE payloads |
| `src/domain/*` | you | the planning model serialized into snapshots |
| `src/constraints/*` | you | hard/soft constraints; names show up in `ui-model.json` |
| `static/index.html` | you | loads `/sf/sf.css`, Font Awesome, `/sf/sf.js`, then the app script |
| `static/app.js` | you | the neutral shell you are extending |
| `static/sf-config.json` | you | human-authored `title`/`subtitle` (some apps add `defaultDemoId`) |
| `static/generated/ui-model.json` | CLI | regenerated by `solverforge generate`/`destroy`; do not hand-edit |
| `/sf/*` at runtime | solverforge-ui | embedded components, fonts, vendor libs, served by `solverforge_ui::routes()` |

Mount template (do not change the seam):

```rust
let app = api::router(state)
    .merge(solverforge_ui::routes())      // serves /sf/*
    .fallback_service(ServeDir::new("static"));
```

Version pinning: the component API is whatever `solverforge-ui` version the app
pins in `Cargo.toml`/`Cargo.lock`. Confirm it before using a detail; the repo's
`README.md` at that version is the API contract. The current `solverforge-cli`
scaffolds the latest published line.

## The boot contract

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>App — SolverForge</title>
  <link rel="stylesheet" href="/sf/sf.css">
  <link rel="stylesheet" href="/sf/vendor/fontawesome/css/fontawesome.min.css">
  <link rel="stylesheet" href="/sf/vendor/fontawesome/css/solid.min.css">
  <link rel="icon" href="/sf/img/ouroboros.svg" type="image/svg+xml">
  <!-- only if you use the map module -->
  <link rel="stylesheet" href="/sf/vendor/leaflet/leaflet.css">
  <link rel="stylesheet" href="/sf/modules/sf-map.css">
  <!-- only if you load Gantt -->
  <link rel="stylesheet" href="/sf/vendor/frappe-gantt/frappe-gantt.min.css">
</head>
<body>
  <div id="sf-app"></div>
  <script src="/sf/sf.js"></script>
  <script src="/app.js"></script>   <!-- classic script; SF is a global -->
</body>
</html>
```

`SF` is a global namespace. A classic script uses `SF.createHeader(...)`; a
module imports nothing and reads `globalThis.SF`. Never bundle or npm-install
solverforge-ui — the runtime integration path is the embedded `/sf/sf.js`.

Optional vendor scripts when the surface needs them:

```html
<script src="/sf/vendor/leaflet/leaflet.js"></script>
<script src="/sf/modules/sf-map.js"></script>          <!-- adds SF.map.* -->

<script src="/sf/vendor/frappe-gantt/frappe-gantt.min.js"></script>
<script src="/sf/vendor/split/split.min.js"></script>  <!-- for SF.gantt -->
```

## `static/generated/ui-model.json`

```json
{
  "entities":   [{ "name": "shift", "plural": "shifts", "label": "Shift" }],
  "facts":      [{ "name": "employee", "plural": "employees", "label": "Employee" }],
  "constraints":["Assigned shift", "Required skill"],
  "views": [
    {
      "id": "shift-employeeIdx",
      "kind": "scalar",
      "label": "Shift · employeeIdx",
      "entity": "shift",
      "entityPlural": "shifts",
      "sourcePlural": "employees",
      "variableField": "employeeIdx",
      "allowsUnassigned": true,
      "scalarHooks": {},
      "countableRange": null,
      "listMetadata": null
    }
  ],
  "scalarGroups": [],
  "conflictRepairs": []
}
```

- `kind` is `scalar` (entity → one value) or `list` (entity → ordered elements).
- `variableField` is the solution field holding the assignment (`employeeIdx`, a
  `deliveryOrder`, …). Scalar values are **indexes into `sourcePlural`**, or a
  number inside `countableRange` (`{from, to}`, half-open).
- `views[].label` is `"<Entity> · <field>"`; rewrite labels only via the CLI or
  an app-owned override file.
- `constraints` is a list of names with no type. To render hard/soft dots
  correctly, derive the type from `src/constraints/*.rs` and build
  `{ name, type: 'hard'|'soft' }` objects in the app (the status bar accepts
  both shapes; objects give accurate labels and dot colours).
- Some finished apps hand-author richer `views[]` with custom `kind`s
  (`schedule-by-employee`, `schedule-by-location`) and dispatch on them through a
  renderer registry. That is an option, but only if the project no longer
  regenerates this file — otherwise the CLI clobbers it.

## Extension patterns

### A. Extend the single-file shell (small apps)

The scaffold's `static/app.js` is already a complete shell. Keep its top-to-
bottom structure and change only:

1. Tabs: replace/augment the generated `views` tabs with domain-named views.
2. Renderers: replace `renderViews` content builders with domain builders.
3. Overview/KPI panel: add domain summary cards if helpful.
4. Data + API tabs: leave them; they are the escape hatch.

This keeps one file and zero build steps. Use it when the whole UI is under
~500 lines.

### B. Modular shell (non-trivial apps)

Split the app into focused ES modules, as `uc-hospital` does:

```
static/
  index.html                  # mounts SF, calls bootApp()
  sf-config.json
  generated/ui-model.json
  app/
    main.mjs                  # boot: config → shell → controller → render
    shell/
      config-loader.mjs       # validates /sf-config.json + ui-model.json
      app-shell.mjs           # header, panels, footer, modal, lifecycle markers
      solver-controller.mjs   # thin adapter over SF.createSolver
      data-panel.mjs          # raw model tables
      api-guide.mjs           # REST endpoint list
    views/registry.mjs        # kind → render function table
    schedule/                 # domain transforms (pure, testable)
      presentation.mjs        # records → { startMs, endMs, label }
      grouping.mjs            # records → lanes
      rail-renderer.mjs       # lanes → SF.rail.createTimeline model
      datetime.mjs            # parse backend timestamps TZ-free
    schedule/analysis-modal.mjs
```

Principles that made this work:

- `main.mjs` owns wiring only; it never builds geometry.
- Transform modules are pure functions: plan JSON in, component config out. They
  are unit-tested without a DOM.
- One adapter (`solver-controller.mjs`) wraps `SF.createSolver`; the rest of the
  app never calls solver methods directly.
- Unknown `view.kind`s render a message, never crash.

### Canonical shell skeleton (either pattern)

```js
function renderAndSync(snapshot, meta) {
  try {
    if (snapshot && snapshot.solution) render(snapshot.solution);
  } finally {
    syncMarkers(meta);
  }
}

var backend = SF.createBackend({ type: 'axum', baseUrl: '' });
var statusBar = SF.createStatusBar({ constraints: typedConstraints });
var solver = SF.createSolver({
  backend: backend,
  statusBar: statusBar,
  onProgress: function (meta) { syncMarkers(meta); },
  onSolution: function (snapshot, meta) { renderAndSync(snapshot, meta); },
  onPaused:   function (snapshot, meta) { renderAndSync(snapshot, meta); },
  onCancelled:function (snapshot, meta) { renderAndSync(snapshot, meta); },
  onComplete: function (snapshot, meta) { renderAndSync(snapshot, meta); },
  onFailure:  function (message, meta, snapshot) { renderAndSync(snapshot, meta); },
  onAnalysis: function (analysis) { lastAnalysis = analysis; },
  onError:    function (message) { console.error(message); },
});

var header = SF.createHeader({
  logo: '/sf/img/ouroboros.svg',
  title: config.title,
  subtitle: config.subtitle,
  tabs: tabs,
  actions: {
    onSolve:   function () { startSolve(); },
    onPause:   function () { solver.pause().catch(log); },
    onResume:  function () { solver.resume().catch(log); },
    onCancel:  function () { solver.cancel().catch(log); },
    onAnalyze: function () { openAnalysis(); },
  },
  onTabChange: function (id) { showPanel(id); },
});
app.appendChild(header);
statusBar.bindHeader(header);
app.appendChild(statusBar.el);
```

`render(plan)` must deep-clone: `currentPlan = JSON.parse(JSON.stringify(plan))`.

Panel switching is plain DOM: give each panel `.sf-content` and toggle
`style.display` in `onTabChange`. Some apps use an app CSS class (`.is-active`)
instead; either is fine, but keep it one mechanism.

## CSS layering

- Reuse tokens: `--sf-emerald-*`, `--sf-gray-*`, `--sf-space-*`,
  `--sf-shadow-*`, plus the `sf-table`, `sf-card`, `sf-badge`, `sf-btn` classes.
- Add one app stylesheet (`static/app.css`) only for layout the components do not
  provide: page grids, responsive reflow, app-specific density, map/route cards.
- Scope every app rule under an app-prefixed root class
  (`body.solverforge-deliveries-app`, `.fsr-map-shell`). Never restyle `sf-*`
  selectors globally; force light mode only if the component set requires it
  (`color-scheme: light`).
- The timeline's dense geometry is intentional. If you must tighten it, scope the
  overrides to your app root and keep items legible (min width, no overlap).

## Safe HTML

Text is rendered as text by default. The only opt-in HTML fields are:

| Factory | Field |
| --- | --- |
| `SF.el(tag, attrs, …)` | `attrs.unsafeHtml` |
| `SF.createModal` | `config.unsafeBody` |
| `SF.createTabs` | `tabs[].content.unsafeHtml` |
| `SF.createTable` | `cells[].unsafeHtml` |
| `SF.gantt.create` | `unsafePopupHtml`, `columns[].render(task).unsafeHtml` |

Use them only with trusted content, and run any backend string through
`SF.escHtml` first. Prefer building DOM nodes for analysis tables, as
`uc-hospital` does.
